Resumen para mantenedores

Este bloque está pensado para copiarse tal cual a un issue de GitHub.

Analizamos el monorepo de Kaddo (revisión f7325f9, v3.144.1) con SonarQube Community Edition 26.7.0 y el perfil «Sonar way» para TypeScript. Es un aporte externo no solicitado: el objetivo es compartir una lectura de mantenibilidad y determinismo, y ofrecer ayuda concreta, no juzgar el proyecto.

El alcance cubre 310 archivos fuente (54.723 líneas) en packages, apps/docs y scripts, más 203 archivos de test. Se revisaron los 1.828 issues completos vía API y cada hallazgo destacado se verificó contra el código fuente en la revisión analizada.

Los resultados positivos son claros: 0 vulnerabilidades y 0 security hotspots, duplicación baja (2,4%), una estructura de monorepo limpia y una automatización de release sólida (provenance npm, guards de sincronización y smoke tests del paquete MCP publicado). Gracias por mantener Kaddo como open source bajo licencia MIT: la arquitectura del monorepo y el cuidado del release son de lo mejor que vimos en este análisis.

Una aclaración importante sobre el dashboard: la cobertura 0,0% significa que no se importó ningún reporte de cobertura al analizar; NO significa que no existan tests. El repositorio tiene 203 archivos de test (Vitest/Playwright). Medir e importar el lcov real es una de las mejoras propuestas.

Los riesgos reales que encontramos son acotados y concretos: 22 llamadas a sort() sin comparador que afectan el determinismo de IDs, exports y listados MCP; 2 ternarios con ramas idénticas; 1 test sin assertions; y 8 funciones con complejidad cognitiva superior a 100. En cambio, 568 de los 1.828 issues (31%) corresponden a una sola regla mecánica de estilo (push consecutivos, S7778): inflan el conteo pero no representan riesgo estructural.

Proponemos un roadmap en olas, cada una pensada como un issue o PR independiente (§9), y ofrecemos preparar los PRs que el equipo decida priorizar. Este informe no modifica código del proyecto. Todo el detalle, con snippets verificados y una propuesta de CI modular, está en las secciones siguientes.

8.1 Prerrequisitos antes de commitear (orden importa)

  1. Renombrar: sacar el sufijo -proposed, actualizar los uses: y retirar el ci.yml viejo. Si se commitean tal cual, los triggers se duplican.
  2. .eslintrc.json: sumar env.browser y jsx-a11y para packages/admin (.tsx). Sin eso, el job de lint nace rojo (hoy pnpm lint solo mira .ts y nunca corrió en CI).
  3. @vitest/coverage-v8 (matching vitest 1.6) en devDependencies raíz: sin el provider, --coverage prompting de instalación y el job se cuelga.
  4. SonarCloud: crear org/proyecto, cargar el secret SONAR_TOKEN y reemplazar REPLACE_WITH_YOUR_ORG. Alternativa: mantener solo el SonarQube local para auditorías profundas y no cablear SonarCloud (decisión abajo).
  5. Branch protection: requerir únicamente «CI Summary» (+ dependency-review si se quiere). Un solo check, no seis.
  6. Secret scanning + push protection de GitHub: activar en settings del repo (gratis para públicos). No es un workflow.
  7. SHA-pin de sonarcloud-github-action y softprops/action-gh-release antes de commitear (hoy quedan por tag mayor, marcado en comentarios).

8.2 Lo que la propuesta deliberadamente NO hace

  • CodeQL en cada PR (alargaría el camino crítico; va semanal + main).
  • Sonar/Trivy como required checks del PR (corren post-merge; el PR ya tiene lint, tests, build y smoke).
  • Matriz de OS (windows/macos) en la suite principal: el smoke MCP ya cubre Node 22/24; sumar OS es una decisión de costo de latencia, no de minutos.
  • Tocar los guards existentes de release: se conservan enteros y se les suma la suite paralela como precondición.

10. Cómo reproducir este análisis

El análisis es reproducible con herramientas públicas y gratuitas; no requiere acceso a infraestructura privada. Resumen (el detalle de parámetros está en la tabla de §1):

  1. Servidor: SonarQube Community Edition 26.7.0 en Docker, con el perfil «Sonar way» para TypeScript (404 reglas activas).
  2. Proyecto: crear un proyecto con key kaddo y generar un token de análisis.
  3. Escáner: SonarScanner CLI 8.0.1 (Docker, Java 21) ejecutado desde la raíz del workspace pnpm, con sonar.sources=packages,apps/docs,scripts, los 6 directorios de tests Vitest/Playwright como sonar.tests, y exclusiones de node_modules, dist, public, assets y *.d.ts.
  4. Lectura de resultados: API del servidor — measures/component, measures/component_tree, issues/search (paginación completa), qualitygates/show, rules/show.
  5. Cobertura (recomendada): ejecutar la suite Vitest con proveedor de cobertura lcov e importar el reporte con sonar.javascript.lcov.reportPaths para reemplazar el 0,0% del Zero Coverage Sensor por una medición real.

Sin cobertura importada, el sensor «Zero Coverage» muestra 0,0% aunque existan tests: es el matiz más importante al reproducir el dashboard. El escaneo de la revisión f7325f9 terminó en 33 s (exit 0).
